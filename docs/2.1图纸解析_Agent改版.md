# 2.1 图纸解析 · Agent 改版

## 1. 改了什么

| 项 | 改版前 | 改版后 |
| --- | --- | --- |
| Agent 引擎 | 平台自研单轮问答（qwen/openai 文本模型） | **直接使用 open-claude 的 `Conversation`**，带完整工具循环 |
| 入口 | 每个页面右下角的悬浮气泡，点开才有 | 悬浮气泡**全部移除**；2.1 页面左侧常驻对话 |

## 2. 后端：`backend/services/oc_agent.py`

不复制、不改写 open-claude，只做三件事：

1. 把仓库内 `open-claude/` 加入 `sys.path`，按项目实例化它的 `Conversation`
   （`permission_mode="always_allow"`，无终端可应答 y/n）；
2. 在它的工具表上追加 5 个平台工具，并在 `open_claude.repl.execute_tool` 的调用点
   前置一层分派；
3. 把流式输出转成 SSE 事件（`text` / `tool_use` / `tool_result` / `error` / `done`），
   帧格式与 open-claude 自带的 web 桥一致。

### 平台工具

| 工具 | 作用 |
| --- | --- |
| `GetProjectState` | 项目状态：图纸、附件、是否已解析、零件/标准件数量、平均置信度 |
| `ListParts` | 零件清单摘要 |
| `GetPartDetail` | 单个零件的特征、材料、公差、溯源 |
| `GetOpenQuestions` | 待澄清问题 |
| `RequestParse` | **只发请求，不执行解析** |

### 三个刻意的约束

- **只读文件系统**：`Write` / `Edit` / `Bash` 既从模型可见的工具表里摘掉，也由
  `OC_READONLY_FS` 在执行层拦住（覆盖子代理）。CLI 不受影响。
- **工作目录 = 项目数据目录**（`DATA_DIR/<project_id>`），所以 `Read`/`Glob`/`Grep`
  看到的是这份图纸、附件与生成的几何文件，而不是整个代码仓库。
- **解析只有一个入口**：`RequestParse` 不自己解析，它带回 `ui_action: "parse"`，
  前端据此点击 `#btnParse` —— 也就是 app.js 原有的那条流水线。
  否则平台会有两套解析实现，结果对不上时无法排查。

### 关于工具分派的实现方式

open-claude 的 `_execute_pending_tools` 把非 Agent / 非 MCP 的工具统一交给模块级的
`execute_tool()`。这里替换 `open_claude.repl.execute_tool` 为一个包装函数：命中平台
工具就自己处理，否则原样转交。权限检查、PreToolUse/PostToolUse 钩子、流式与自动压缩
全部保持 open-claude 原生行为。

代价是一处受控的模块级替换。备选方案是 fork 一份 `repl.py`，那会带来一份需要长期
跟随上游的副本 —— 耦合面更大。包装函数保留了 `__wrapped__` 便于排查与还原。

### 接口

```
GET  /api/projects/{id}/agent/meta    模型、工具、技能、profile、cwd（供左侧工具栏）
POST /api/projects/{id}/agent/send    一轮对话，SSE 流式返回
POST /api/projects/{id}/agent/new     清空上下文（不动业务数据）
POST /api/projects/{id}/agent/model   切换模型
```

`meta` 在 Agent 不可用时返回 `{available:false, reason}` 而不是 500 —— 页面需要显示
「为什么用不了」，且图纸解析等平台功能不应受影响。

## 5. 工艺推荐 / 成本测算移到左侧（后续调整）

原机制是「左侧点零件 → 右侧跳转出零件详情 → 详情里再点工艺/成本」。
现在把后两步也收到左边：**零件清单里每个零件下挂两个子按钮**。

```
#tree
└── div.part[data-part-id]                 点击：选中零件 + 展开子按钮
    └── div.part-subactions                 同一时刻只展开一个
        ├── div.part-nav                    复用原按钮样式，外观不变
        │   ├── button 工艺推荐
        │   └── button 成本测算
        └── div.part-inline-host            分析面板就地渲染在这里
```

- 分析面板复用 `inline-analysis.js` 的 `CadInlineAnalysis.open(mode, {host, ...})`，
  只是把 `host` 从右侧的 `#inlineAnalysisHost` 换成该零件下的容器 —— 没有第二份实现。
- 右侧零件详情**去掉**了这两个按钮，只保留 3D 视图、零件信息与几何/图纸下载。
- 子按钮 `stopPropagation`，否则点它会连带触发外层零件行的重新选中。
- 面板文案跟按钮统一改叫「工艺推荐 / 成本测算」（原为「工艺拆解 / 成本分析」），
  否则点「工艺推荐」会弹出标题写「工艺拆解」的面板。接口路径仍是 `process` / `cost`，
  未受影响；独立的成本分析页（`cost.js`，属报价流程）不在本次范围内。

### 顺带修掉的一个布局缺陷

工艺推荐面板的三栏网格靠 `@media(max-width:1050px)` 收成两栏。媒体查询看的是**视口**
宽度而非容器宽度，所以在宽屏下把它放进较窄的抽屉会横向溢出。已按容器显式收窄
（`.oc-drawer .inline-process-grid`），并把抽屉从 520px 放宽到 760px。


## 6. 输入资料回看、处理过程可见、拆解时检索零部件库（后续调整）

### 6.1 本次输入的图纸与文档

问题：进对话框之后没有地方展开之前输入的资料。＋ 菜单里的抽屉能**改**，
但要**看**得先猜它在哪一组下面。

现在把它直接摆进对话（`#ocInputAssets`，在设计意图卡之后）：需求原图、技术文档
与补充视图、补充技术说明，默认折叠只露条数，点「展开」才占版面。文件名是链接，
指向已有的 `GET /api/projects/{id}/source` 与 `/attachments/{name}`，没有新增下载通道。

### 6.2 处理过程显示在对话里

解析、几何生成这些都跑在后台任务里，进度原本只在右侧任务条上刷。现在
`app.js` 的 `pollTask` 每轮额外派发一个 `agent:task-progress` 事件：

```
{ label, taskId, status, progress, error }
```

`agent-chat.js` 把它渲染成对话里的一张时间线卡（`.oc-process-card`）。两个细节：

- 轮询会反复读到同一条进度，所以按文本去重（`processCard.seen`），
  否则时间线会变成刷屏而不是「步骤」。
  > 这个做法后来被 §15.2 推翻：单值 `progress` 本身会丢步骤，去重方式也换成了按
  > 日志下标续播。本节保留原状以说明当时的判断。
- 进度不是新通道，只是既有轮询结果的一个旁路 —— 任务本身的成败判定没有变。

### 6.3 图纸拆解时检索零部件库

拆解出零件只是第一步。工艺评估真正要回答的是**哪些库里已经有**。这一步现在
做在拆解流程里（`backend/services/component_match.py`），不再留给人事后翻库。

```
IR.parts ─→ build_query()  特征 → {length,width,thickness,diameter,hole_diameter}
         ─→ kb_repo.recommend_components()   包络粗筛 → 参数精筛 → 特征相似
         ─→ 三档结论
              reuse   ≥0.90 或 match_type=exact   可直接复用
              modify  ≥0.55                        可改制（附 gap_notes 差异说明）
              new     其余                          未匹配，按新制评估
```

- **打分全程不经模型**。同一份 IR 反复跑结果必须一致，否则同一张图两次评估会给出
  不同的复用建议。
- 判为 `new` 时会把候选编码清空。漏斗的召回门槛（0.35）比「可改制」低，弱候选照样
  会被带回来；不清空的话界面上会出现一条并不成立的命中。候选仍留在 `candidates`
  里供人工翻查。
- 检索挂在解析任务的最后一步，用 `tasks.report_progress` 逐件上报，因此过程会经
  6.2 的通道出现在对话里：

  ```
  零部件库检索开始：3 个零件 × 库内 12 条记录
  检索零部件库（1/3）：P-001 设备安装底板
    ↳ 命中 CMP-PLT-0001（可直接复用，100%）
  检索零部件库（2/3）：P-002 异形壳体
    ↳ 库内无同类件，按新制评估
  零部件库检索完成：可复用 1、可改制 1、未匹配 1
  ```

  前端按「命中」/「无同类件」给不同标记，扫一眼就知道库里有没有。
- 检索失败**不能让已经拿到的 IR 作废** —— 解析任务里整段 try/except，失败只记审计。
- 结果存在 `store.save_component_match`，接口 `GET|POST /api/projects/{id}/component-match`；
  同时尽力而为地写一份到 DA 的 `wip_component_match`（DA 库当前仍与主流程并行，
  写不进去只记一条 `component_match_da_skip`）。
- 对话里的汇总卡（`.oc-match-card`）每次重渲染前先移除上一张，重复解析不会堆卡。

## 7. 工艺推荐 / 成本测算接入知识库检索（后续调整）

第 6.3 节只让**图纸拆解**去查了零部件库。工艺推荐和成本测算当时仍是纯模型输出 ——
模型能编出一条看着合理的工艺路线，但工序编号对不上车间实有设备，单价也追不到
任何一条价格记录。报出来的工期和报价没有依据，拿不去谈。

现在这两步在调模型**之前**先查库，同一套模式：确定性检索 → 进度进对话 →
结果既喂给模型也存下来当依据。

```
backend/services/process_lookup.py     工艺库检索
backend/services/cost_lookup.py        成本库检索
```

### 7.1 工艺库检索

三层，全程不经模型：

1. **路线模板**：优先取匹配到的库内零部件挂的 `default_route_code`（同一个零件
   以前怎么做的，就还怎么做）；没有匹配件时按 类别／材料类别／批量 召回打分。
2. **工序**：展开路线的工序序列，取 `setup_min`、`unit_min_formula`、
   `default_equipment_class`，并带出该设备类下的具体设备。
3. **特征补漏**：按零件特征再召回一遍工序，落在路线之外的列为**补充工序**候选；
   一个特征连候选都召不到，就是**库内空白**，必须走工艺开发。

第 3 步是这个模块存在的主要理由：路线模板是按类别做的，具体零件多出来的特征
（底板上多一圈密封槽）不会自动进模板，不补漏就会被整条漏掉。

**但补漏必须按材料收敛。** `kb_process_step.applicable_feature` 是很粗的几何标签 ——
`plate` 同时挂在粗铣、折弯、光刻、极片涂布上。第一版没做材料过滤，一块 Q235 底板
被召回了 26 道"补充工序"，里面有光刻和极片涂布；成本侧继承了这些工序的设备类，
又凭空多出 23 条"费率缺失"。现在按 `applicable_material` 收敛：

- 有材料类别（按牌号反查 `kb_material.category`）→ 用它；
- 图纸没写牌号 → 退用路线模板自己的 `applicable_material`，至少把行业圈对；
- 两者都没有 → **不召回**，只留一条「先确认材料牌号」的说明。宁可不给，
  也不给一堆荒唐候选。

修正后同一块底板的补充候选是「折弯成型、焊接」两道，成本缺口从 23 条降到 5 条
（且这 5 条是真的：那几个设备类在库里确实没录折旧费率）。

### 7.2 成本库检索

1. **物料价**：按牌号反查物料编码，再按**测算时点**取价。带上 `price_id` 与来源，
   事后能复现这次测算用的是哪条价。图纸没写牌号时退用匹配件的默认物料，
   并在 `source` 里标明这是推断。
2. **费率**：按工艺检索给出的设备类逐个取 labor / equipment_dep，再取全厂口径的
   energy / overhead / logistics。**回退到 global 必须显式标记** —— 拿一条全厂通用
   人工费率当专机费率用，成本会低估一大截，这是最容易出错的一处。
3. **计价系数**：良率跟零件类别走，废品率跟材料类别走，毛利/税率是全公司口径。

查不到的一律进 `gaps`，直接变成待询价／待补录，**绝不静默取默认值**。

### 7.3 接线

- `process.decompose_process` / `cost.analyze_cost` 各加一个 `library` 参数，接收
  `as_prompt()` 压出来的摘要。给了它，模型就该在企业既有编号和标准工时上排产；
  没给（库为空或检索失败），仍退回原来的通用工艺口径 —— 那条「不得编造企业资源
  编号」的老约束保留不变。
- 检索**失败一律降级为"没查到"**，绝不能挡住推荐：库是辅助依据，不是前置条件。
  失败只记一条 `process_lookup_failed` / `cost_lookup_failed` 审计。
- 报告与 plan/analysis **分开存**（`store.save_process_lookup` / `save_cost_lookup`）。
  这两份是**依据**，人工编辑工艺路线不该把依据一起改掉，依据也不该跟着 plan 走版本。

### 7.4 界面

- `inline-analysis.js` 的 poll 循环也派发 `agent:task-progress`，所以检索的每一步
  跟拆解一样显示在 Agent 对话里。
- 工艺推荐面板右栏、成本测算面板下方各多一张**「库内依据」卡**：工序编号来自哪条
  路线模板、单价来自哪条 `price_id`；补充工序与回退费率用橙色标出。
- Agent 自己也能查：新增平台工具 `LookupProcessLibrary` / `LookupCostLibrary`，
  用户直接问「这个零件怎么做」「材料什么价」时，答案有库可依而不是现编。

### 7.5 接口

```
GET  /api/projects/{id}/parts/{part_id}/process-lookup    工艺库检索报告
GET  /api/projects/{id}/parts/{part_id}/cost-lookup       成本库检索报告
POST /api/projects/{id}/parts/{part_id}/library-lookup    只重查依据，不调模型
```

最后一个是给"补了费率、改了路线之后想看依据变了什么"用的 —— 不必为此重跑一次
要花钱的工艺推荐或成本测算。

### 7.6 测试

`tests/test_library_lookup.py`：kb_repo 全部打桩，断言召回口径、缺口不被默认值
掩盖、回退标记、以及接线（检索排在模型调用之前、失败降级、依据与 plan 分离）。


## 8. 两个悬浮小窗取代左侧栏（后续调整）

第 3 节把对话设置做成了一条 214px 的整高左侧栏。它常驻占版面，而里面真正常用的
只有「模型」和「新对话」两项。现在收成两个悬浮小窗，页面主体全部让给工作区。

## 9. 悬浮小窗的三处调整

### 9.1 任务文件直接列出来

第 8.3 节做成了「小窗显示总数 → 点开弹窗看清单」。多一次点击换不来什么，
现在清单直接渲染在右窗里，标题栏只留计数和一个刷新按钮，弹窗整套删掉
（`.oc-modal*` 样式、`openFiles/closeFiles`、Esc 关闭分支）。

小窗本来就有 `max-height: calc(100vh - 78px - 88px)` + `overflow-y: auto`，
文件多了自己滚，不会盖住页脚的「上一步 / 解析报告」；也和左窗一样能整个收起
（`#ocFilesToggle`），收起后标题栏仍显示文件数，一眼看得出有没有新产出。

两个标题栏因此统一成「容器 + 折叠开关按钮」：按钮不能嵌套，右窗的「刷新」必须是
折叠开关的兄弟节点而不是子节点。

计数和列表由同一次请求写入，不会出现「显示 5 条但列出 3 条」。

### 9.2 模型选择 → 模型参数设置

原来点开只能换模型。现在是一个完整的设置面板：

| 项 | 范围 | 说明 |
|---|---|---|
| 模型 | open-claude 的 AVAILABLE_MODELS | |
| 深度思考 | 开/关 | |
| 温度 | 0 ~ 1，可留空 | 留空 = 用模型默认值 |
| 最大输出 tokens | 256 ~ 64000，可留空 | |
| 思考预算 tokens | 1024 ~ 64000 | 开启深度思考后生效 |
| 单轮最多工具调用轮次 | 1 ~ 100 | 防止工具循环跑飞 |
| API Key | 写入型 | |

```
GET /api/projects/{id}/agent/settings
PUT /api/projects/{id}/agent/settings   # 未传的字段保持不变
```

四条约束：

- **取值范围在后端夹住**（`_clamp`），不信任前端。temperature 传 5 会让整轮请求被
  API 打回，错误信息还很难懂。实测 `temperature:5 → 1.0`、`max_iterations:999 → 100`。
- **密钥永不回明文**。`GET` 只返回 `api_key_set` 与打码的 `api_key_hint`
  （`sk-ant-…qwAA`）。回传明文等于把它送进浏览器缓存和日志。
- **改密钥限管理员**。`ANTHROPIC_API_KEY` 是进程级的，改了对本服务**所有项目**
  生效；其余参数是会话级的，工程师即可改。审计只记「改过密钥」这件事，不记值。
- **换密钥要重建 client**。open-claude 在构造 `Anthropic()` 时就把 key 读进去了，
  只改环境变量等于没换。

参数改动即时生效于下一轮对话 —— 后端改的是同一个 Conversation 的 profile，
不需要新建会话。**但设置只存在内存里，服务重启后回到 profile 默认值。**

### 9.3 新对话 → 本次任务从头开始

原来这个按钮只清对话上下文，业务结果原封不动 —— 用户想「重来一次」时它帮不上忙。
现在 `POST /agent/new` 改成重置整个 2.1 阶段（`store.reset_parse_stage`）：

**清掉**：ir、drawing_analysis、verification_report、model_lookup、component_match、
geometry、drawings、process、cost、process_lookup、cost_lookup、ai_results，
以及 Agent 对话上下文。

**保留**：

- 已上传的原图与技术文档 —— 「从头开始」是拿同一份图纸重新解析，不是把图纸删掉；
- 需求单（1.x 的产出，不属于本步骤）；
- 版本快照 `versions` —— 重来一次不该把可追溯的历史一并抹掉；
- 2.2 之后各步的结论 —— 替用户决定删掉太越权，改为立起 `derived_results_stale`，
  界面照旧提示「请重新生成下游结果」。

两个细节：

- 会丢结果，所以**前端先 confirm**，把要清掉什么逐条列出来。
- **Agent 不可用时仍然重置业务产出** —— 模型连不上不该妨碍用户把任务重来一遍，
  所以 `reset_parse_stage` 排在 `oc_agent.available()` 之前。

顺带修掉一处：`.oc-pop` 原本是 `position: absolute`，但坐标取自
`getBoundingClientRect`（视口坐标），页面一滚动弹层就偏，改成 `fixed`。


## 10. 大模型配置统一

改之前平台有**两套互不相干**的模型配置：

| | 首页「模型设置」 | 2.1 页 Agent 小窗 |
|---|---|---|
| 后端 | `qwen_client` 运行时配置 | open-claude Conversation 的 profile |
| 内容 | 视觉/文本/联网模型池 + Key + Base URL | 模型 + 推理参数 + ANTHROPIC_API_KEY |
| 存储 | `data/llm_runtime.json`，重启保留 | 只在内存，重启即失 |
| 前端 | home.js 里一套表单 | agent-chat.js 里另一套表单 |

结果就是「在哪儿改的只在哪儿生效」，两处显示的模型还能对不上。

### 10.1 一份配置

新增 `backend/services/llm_settings.py` 作为唯一真相源。两个接口读写的是同一份快照：

```
GET|PUT /api/llm/settings                        首页入口
GET|PUT /api/projects/{id}/agent/settings        2.1 小窗入口（前者的项目级别名）
```

后者在 main.py 里直接调用前者的函数体，**不是两份实现**，物理上无法再分叉。

**为什么不把 qwen_client 的存储也搬过来**：那是真正在跑推理的路径，模型池降级、
额度耗尽跳过、client 缓存都挂在它上面。`llm_settings` 只做门面，平台侧读写仍然
委托给它；新增的只有 Agent 侧字段（模型 + 推理参数），落盘在 `data/agent_llm.json`
（0600），**重启后仍生效** —— 这是顺带修掉的：Agent 侧原来只存内存。

### 10.2 多模态与语言模型分开选

本任务要读图，所以两类模型必须分别指定：

| 字段 | 用途 | 选错的后果 |
|---|---|---|
| `vision_model` | 图纸解析 | **必须是多模态**；选纯语言模型解析直接失败 |
| `text_model` | 需求抽取、工艺推荐、成本测算 | |
| `web_model` | 型号联网核验 | |
| `agent_model` | 2.1 对话 Agent | |

`PROVIDER_CATALOGS` 里 vision 与 text 是两份独立清单。Qwen 部署下直接用运行时
配置的真实模型池（当前 22 个多模态 / 100+ 语言模型），不是写死的短名单。

**选中某个模型 = 把它提到池首，而不是把池裁成一个** —— 裁掉了额度耗尽时就没有
降级目标了。

### 10.3 前端只有一份面板

`frontend/llm-settings-panel.js` + `.css`，首页对话框与 Agent 弹层共用
`LlmSettingsPanel.mount(container)`。home.js 里原来那套表单
（`homeLlmProvider/Vision/Text`、`saveHomeLlmSettings`、`homeApplyProviderCatalog`）
全部删除 —— 留着就会再分叉。

### 10.4 生效范围

- 平台侧写进 qwen_client，下一次推理调用立刻用新模型。
- Agent 侧通过 `oc_agent.apply_settings()` 推给**所有已经建好的会话**；
  新建会话在 `get_agent()` 里立刻套用全局配置。没有这两步，改设置就只对之后
  新建的会话生效，用户会看到「我明明改了」。

### 10.5 密钥

两个密钥是真的需要分开的（平台走百炼兼容端点，Agent 走 open-claude 的 provider）。
统一的是配置入口和生效范围，不是把两个 provider 硬并成一个。两者都：

- **只写不读**：接口只回 `*_key_set` 与打码的 `*_key_hint`；
- **限管理员**：密钥与平台模型是全服务级的；
- **审计只记字段名**，`changed_fields()` 显式排除任何以 `api_key` 结尾的键；
- 面板保存成功立即清空输入框，密钥不留在 DOM 里。

### 10.6 两个在验证中发现并修掉的缺陷

1. **`exclude_none=True` 让「清空」永远失效。** 面板的数字输入留空会发
   `temperature: null`，但 `model_dump(exclude_none=True)` 把它整个丢掉了 ——
   界面上写着「留空用模型默认值」，实际点了没反应。改成 `exclude_unset=True`，
   才能区分「没传这个字段」和「传了 null」。
2. 参数取值范围统一在 `llm_settings` 夹住（`PARAM_RANGES`），`oc_agent.apply()`
   只负责赋值 —— 校验放两处就会分叉。

### 10.7 验证

起真实服务实测：

- 两个入口返回的快照**逐字段一致**；
- 通过 2.1 小窗写入 → 首页读回一致 → `/api/health` 显示推理路径已换模型
  → 活着的 Agent 会话 `conv.model` 也已跟上；
- 越界值被夹住（`temperature:5 → 1.0`、`max_iterations:999 → 100`）；
- `temperature:null` 能清空，不传该字段则不被改动；
- 密钥在任何响应里都没有明文。

测试见 `tests/test_agent_layout.py::ModelSettingsTests`（13 项）。


## 11. 设置项收敛到六个

第 10 节合并了配置，但面板上摆了十来项（提供商、联网模型、base_url、对话模型、
思考预算、工具轮次、两个 Key……），仍然不知道该改哪个。现在只留六项：

    多模态模型 · 语言模型 · 温度 · 最大 token · 是否思考 · API Key

### 11.1 砍掉的东西去哪了

| 原设置项 | 处置 | 理由 |
|---|---|---|
| 提供商 | 移除 | 换它要改 .env 并重启，是部署动作不是设置动作 |
| API Base URL | 移除 | 同上 |
| 联网检索模型 | 移除，用池首 | 只服务型号核验，有合理默认 |
| 思考预算 / 工具轮次 | 变常量（8000 / 30） | 有合理默认，摆出来只增加选择负担 |
| Agent 对话模型 | **并入「语言模型」** | 见下 |
| 两个 API Key | **并成一个** | 见下 |

### 11.2 为什么能并成一个模型、一把 Key

第 10 节里 Agent 模型与平台模型是分开的，理由是「两个 provider」。但那正是
「两处设置对不上」的残余。实际上 open-claude 的 `get_model_provider()` 按模型 id
**前缀推断** provider，再从对应环境变量取密钥（qwen → `DASHSCOPE_API_KEY` /
`QWEN_API_KEY`）。所以：

- **Agent 用的就是「语言模型」**：`agent_params()` 直接返回 `text_model`。
  改一次，平台的文档分析和 Agent 对话一起变。
- **一把 Key**：保存时同时写进 qwen_client 运行时配置（平台推理路径）和
  `PROVIDER_KEY_ENVS[LLM_PROVIDER]` 里的环境变量（open-claude 取密钥的地方）。

这样「全局统一用同样的大模型配置」才是字面意义上的成立，而不是「统一了入口、
底下还是两份」。

### 11.3 多模态仍然单独选

图纸解析必须多模态，所以 `vision_model` 保持独立。当前部署下两份清单都来自真实
模型池：22 个多模态 / 104 个语言模型，不是写死的短名单。

### 11.4 验证

起真实服务实测：

- 快照字段只剩 `provider / editable / vision_model / text_model / temperature /
  max_tokens / thinking / api_key_set / api_key_hint`（加两份 options）；
- 首页与 2.1 小窗两个入口返回**逐字节相同**；
- 把语言模型改成 `qwen3.7-plus` 后，`/api/health` 的 text_model 与活着的 Agent
  会话 `conv.model` **同时**变成它；
- 越界值仍被夹住，`null` 仍能清空回默认值；
- 密钥无明文泄漏。

所以 snapshot 额外回一份 `active_vision_model` / `active_text_model`（运行时真正

### 12.3 需要注意的一点

这份清单横跨四个提供商，但**平台的实际调用端点由部署时的 `LLM_PROVIDER` 决定**
（当前是 qwen，走百炼兼容端点）。也就是说在当前部署下：

- `qwen3.5-plus` / `qwen3.8-max` 能正常解析到；
- `deepseek-v4-pro` / `deepseek-v4-flash` 取决于百炼是否代理了这两个型号；
- `claude-opus-5` / `gpt-5.6-sol` 需要把 `LLM_PROVIDER` 切到对应提供商并配好

白名单只管"能选什么"，管不了"能不能调通"——后者是部署配置。


## 13. 删掉老调用路线，按模型走官方网关

用户反馈：配了 opus5，但不管是 AI 解析还是多模态调用，跑的都还是老路线。查下来是
**两层老路线叠加**：

1. **网关写死。** `llm_client` 在 import 时按 `.env` 的 `LLM_PROVIDER` 星号导入某一个
   客户端模块，`qwen_client.get_client()` 又固定读部署时配的那一个 MaaS 私有端点
   （`ws-…maas.aliyuncs.com`）。于是选 opus5 只是拿这个 id 去问一个不认识它的网关。
2. **静默降级。** `_model_candidates()` 返回整个模型池，配置的模型一报 403/404/429
   就换成池里的下一个。实测当时的池是
   `('claude-opus-5', 'qwen3.5-plus', 'qwen3-vl-flash', …)` —— opus5 打不通就自动落到
   旧的 qwen 型号，全程没有任何提示。

### 13.1 现在的路线

```
模型 → llm_settings.provider_of() → PROVIDERS[provider]
     → 官方 base_url + 该提供商的 Key
     → anthropic 走 claude_client（原生 SDK），其余走 OpenAI 兼容协议
```

| 提供商 | 官方网关 |
|---|---|
| Anthropic | `https://api.anthropic.com` |
| OpenAI | `https://api.openai.com/v1` |
| 阿里云百炼 | `https://dashscope.aliyuncs.com/compatible-mode/v1` |
| DeepSeek | `https://api.deepseek.com/v1` |

**没有模型池，没有降级链。** 配的哪个就用哪个，失败如实报错并带上模型名。

### 13.2 内容块必须中立

调用方先构造内容块、后发起调用，而这两步之间才知道最终由谁来跑（Anthropic 用
`{"type":"image","source":…}`，OpenAI 兼容用 `image_url`）。所以 `llm_client` 的
`text_block/image_block/attachment_blocks` 产出**中立结构**，在 `run()` 里按目标
提供商翻译。带图走多模态模型，不带图走语言模型。

### 13.3 顺带修掉的三处

- **推理参数原本只对 Agent 生效**：平台自己的解析与分析仍走 `.env` 固定值，
  等于设了没用。现在 `qwen_client` 与 `claude_client` 都从
  `llm_settings.inference_params()` 读温度/最大 token/是否思考。
  温度留空不会被传成 0（那会把模型钉死在贪心解码）。
- **claude_client 的修复重试漏传模型**：第一次用你选的模型，重试时却退回
  `.env` 的 `CLAUDE_MODEL`。已改为两次都用同一个。
- **密钥改为按提供商保存**：选了哪两个模型，面板就只显示哪几行 Key
  （同属一家时只有一行），并同步到环境变量供 Agent（open-claude）使用。
  落盘在 `data/llm_settings.json`（0600），只写不读。

### 13.4 对话框显示每一步的过程与结果

解析任务现在每步都播「在做什么」+「做出了什么」：读取了哪些文件、调用哪个模型、
解析出几个零件/几个待澄清/几条证据。数据库检索连**查询条件**一起播：

```
• 检索零部件库（1/2）：P-001 设备安装底板
  ↳ 查询条件：length=200、width=120、thickness=10、hole_diameter=9，材料 Q235
  ↳ 命中 CMP-PLT-0001 设备安装底板（可直接复用，匹配度 93%）
• 检索零部件库（2/2）：P-002 异形壳体
  ↳ 查询条件：无可用尺寸参数
  ↳ 库内无同类件，按新制评估
```

只报结论的话，匹配不上时无从判断是库里没有还是条件提错了。前端按前导空格把
结果行相对动作行缩进（`.oc-process-step.sub`）。

## 15. 解析视图与检索过程可见（本次）

### 15.1 左侧抽屉：技术文档与视图 → 解析视图

输入的原图与技术文档已经由右侧「任务文件」小窗统一承载，左侧抽屉里再列一遍
是同一份数据两处渲染 —— 改一处就会两边对不上。因此：

- 入口与抽屉标题统一改为**解析视图**；
- 删掉 `#projectEvidence`（原图+附件清单）与 `#attachmentImageGallery`（附件图库），
  连同 `app.js` 里的 `renderProjectEvidence` / `renderAttachmentImageGallery` 一起删；
  只留渲染函数而不留节点，等于留一段永远走 early-return 的死逻辑。
- 保留的就是**解析后的视图**：`#imgStage` 里的原图叠加 `#bboxLayer` 零件标注框，
  点零件清单会在这里高亮。

`DomContractTests` 原本禁止任何 id 从页面消失。这两个是有意删除，因此加了
`INTENTIONALLY_REMOVED` 白名单，并配一条 `test_removed_nodes_have_no_leftover_references`
反向卡住"删了节点却留着渲染代码"。

### 15.2 检索过程为什么"没显示"：progress 是单值字段

零部件识别、工艺推荐、成本测算都调了 `tasks.report_progress`，前端也监听了
`agent:task-progress`，管线是通的 —— 但过程仍然看不见。原因在中间那一层：

```
report_progress → store.update_task(progress="…")   # 单值，后一条覆盖前一条
前端 pollTask     → 每 1200ms 读一次 task.progress    # 只看得到最后一条
```

零部件库检索是**纯本地 SQL 漏斗**，几十条进度往往在一次轮询间隔内全部播完，
于是界面上就"一步都没有"。模型调用类任务因为每步都要等模型，反而看得见 ——
这正是"图纸解析有过程、检索没过程"的原因。

改法是把进度改成**只增不改的日志**：

- `store.append_task_progress(project_id, task_id, line)`：在 `_task_lock` 内追加到
  `progress_log`，同时把 `progress` 更新为最新一条（状态条仍只显示摘要）。
  上限 `PROGRESS_LOG_LIMIT = 400`，防异常循环撑爆任务文档。
- `tasks.report_progress` 改为调它，不再覆盖写。
- `app.js` / `inline-analysis.js` 的轮询把整份 `progress_log` 放进事件的 `log` 字段。
- `agent-chat.js` 按**下标游标**续播（`card.cursor` + `log.slice(card.cursor)`），
  不再按文本去重 —— 两个零件都"库内无同类件"本来就该出现两条，文本去重会折叠成
  一条，看起来像只查了一件。旧任务记录没有 `progress_log` 时退回单条进度。

### 15.3 零部件库也给 Agent 一个工具

工艺库、成本库都有 `LookupProcessLibrary` / `LookupCostLibrary`，唯独零部件库没有，
Agent 只能读解析时跑过的那份缓存 —— 库里新录了件也看不见。补上
`LookupComponentLibrary(part_id?)`：

- 传 `part_id`：现查该零件的匹配结论（编码、匹配度、可复用/可改制/未匹配、
  查询用的尺寸与材料、全部候选与差异说明）；
- 不传：返回整份汇总并落盘 —— 用户常问的是"整台设备有多少能复用"，
  逐件问一遍既慢又容易漏。

与另两个库工具一致：**现查不读缓存**，编码必须来自库里，不得自行编造。

## 16. `List[str]` 字段收到裸字符串导致整份 IR 作废（本次）

### 16.1 现象

```
Claude 输出未通过 schema 校验: 1 validation error for DesignIR
assumptions
  Input should be a valid list [type=list_type,
   input_value='材料按家电常规选…文档未给出牌号', input_type=str]
```

模型只想说**一条**假设，于是给了字符串而不是单元素列表：

```json
"assumptions": "材料按家电常规选用冷轧板，文档未给出牌号"
```

### 16.2 为什么必须修，而且不能只修 `assumptions`

- **代价不对称**：零件、尺寸、公差、证据台账可能全都解析对了，只因为一句附注的
  **容器类型**不对，整份 IR 一起丢。
- **重试也救不回来**：`claude_client.run` 会带着 pydantic 报错重试一次，日志显示
  模型第二次照旧给字符串 —— 这不是提示词问题，靠"再嘱咐一遍"解决不了。
- **不是个别字段**：`backend/models/` 下有 42 个 `List[str]` 字段
  （`assumptions` / `risks` / `highlights` / `warnings` / `open_questions`…），
  每一个都能以同样方式炸掉对应那一步。只改 `ir.py` 等于等着下一步再炸一次。

### 16.3 改法：`StrList`

新增 `backend/models/coercion.py`：

```python
StrList = Annotated[List[str], BeforeValidator(as_str_list)]
```

归一化规则（**只归一容器，不无中生有**）：

| 输入 | 结果 |
| --- | --- |
| `"一条假设"` | `["一条假设"]` |
| `None` / `"  "` | `[]` |
| `["", " ", "有效"]` | `["有效"]` |
| `[{"assumption": "按常规选材"}]` | `["按常规选材"]`（字段是 List[str]，信息没有别处可放） |
| `{...}` 等无法识别的 | **原样放行**，让真正的结构错误照常暴露 |

17 个模型文件里的 `List[str]` 全部换成 `StrList`。

`model_json_schema()` 产出的仍然是 `{"type":"array","items":{"type":"string"}}` ——
**给模型看的约定没有放宽**，只是解析端不再因为这种无歧义的写法而整份作废。

### 16.4 顺带

`claude_client.run` 校验失败时的文案写死了「Claude 输出未通过 schema 校验」。
按第 13/14 节的路由改造，这条路径跑的是「模型设置」里选中的模型，报错里应当出现
那个名字，否则和用户在界面上看到的对不上。已改为 `{route['model']} 输出未通过…`。

### 16.5 测试

`tests/test_ir_normalization.py::StrListCoercionTests` —— 逐条钉住上表的归一化规则、
JSON schema 未变，外加一条**全量扫描**：遍历 `backend/models` 下所有模型，
凡是注解仍为裸 `List[str]`（没挂 `as_str_list`）的字段一律报出来。
新加字段时漏用 `StrList` 会直接测试失败，而不是等到线上又炸一次。
（扫描逻辑本身用一个故意写成裸 `List[str]` 的哨兵类验证过不是空跑。）

## 17. 结果按钮从对话首条移到常驻底部（本次）

「零件清单 N」「待澄清问题 N」原本挂在**设计意图卡**里 —— 那是对话的第一条消息。
解析完看得见，但只要再聊几轮，它就被新消息顶到上面，要往回翻才找得到；而这两个
按钮恰恰是全程都要随手点的。

改为常驻对话**底部**，每轮对话结束后重新置底：

- `index.html`：`#ocResultActions` 从 `.oc-intent-card` 里挪出来，成为 `#ocTinner`
  的直接子节点，排在首屏引导语之后。
- `refreshResultChips()` 末尾 `tinner.append(resultBox)`。append 一个**已在文档里**的
  节点是「移动」而不是「复制」，所以不会出现第二份按钮条。
- 触发点：每轮对话结束（`send()` 的 `finally`，出错结束也算）、后台任务成功、
  `agent:parse-done`、`agent:ir-rendered`。
- `agent:parse-done` 里改成等 `renderComponentMatch()` 落地后再置底 —— 汇总卡是异步
  取的，不等它就会插在按钮条后面，DOM 顺序和视觉顺序对不上（读屏与 Tab 序要用）。

### CSS 兜底

`.oc-tinner` 是 `flex-direction: column`，因此给 `.oc-result-actions` 一个
`order: 1`（其余子项默认 0）就能保证它**视觉上**永远最后。JS 置底管 DOM 顺序，
CSS `order` 管视觉顺序 —— 这样即使将来又多一处异步渲染忘了触发置底，按钮条也不会
被顶上去。原来的 `margin-top: 11px` 是为了在意图卡内部拉开距离，现在由
`.oc-tinner` 的 `gap: 16px` 接管，已去掉。

测试：`LayoutStructureTests.test_result_chips_sit_at_the_bottom_not_in_the_intent_card`
（顺序 + **缩进层级**，缩进比 `#ocEmpty` 深就说明它还嵌在某张卡里）与
`test_chips_are_re_anchored_after_each_turn`（置底调用、`finally` 里的触发、CSS order）。

## 18. Agent 通过对话修改零件参数（本次）

### 18.1 改之前的状态

**不能。** 2.1 页的 Agent 工具集是全只读的：`Write` / `Edit` / `Bash` 既从模型可见的
工具表里摘掉、又由 `OC_READONLY_FS` 在执行层拦住，8 个平台工具全是查询，
`RequestParse` 也只是发请求。用户说「把底板厚度改成 3mm」，它最多只能告诉你去哪里
手工改。

但这个能力其实**早就实现过**：老的单轮 `workbench-chat` 有一条经过安全设计的受控
改写路径（白名单字段、按特征类型二次校验、版本快照、审计）。它的对话界面在 Agent
上线时被替换掉了，于是这段逻辑成了孤儿 —— 有实现，没有入口。

### 18.2 改法：把改写逻辑提出来，两个入口共用

新增 `backend/services/part_edit.py`，`workbench-chat` 与 Agent 都调它。
**不允许有第二份实现** —— 两份白名单一定会漂移，某天其中一条路允许改另一条不允许，
而这类差异只有出事才会被发现。

服务端强制的约束（不依赖模型自觉）：

| 允许 | 拒绝 |
| --- | --- |
| `name` / `quantity` / `material.spec` | 新增或删除特征 |
| **已有**特征的数值字段，按 `type` 逐类白名单 | 修改特征 `type` |
| — | 一次改多个零件 |
| — | 非正尺寸（`x` / `y` 是相对坐标，可为负） |
| — | 导入的精确 STEP/STP 实体（改 IR 改不动真实实体，只会让两者脱节） |

白名单是**白名单不是黑名单**：新增特征类型时，"忘了禁"比"忘了放行"危险得多。

### 18.3 新平台工具 `UpdatePartParameters`

```
UpdatePartParameters(part_id, name?, quantity?, material_spec?,
                     feature_updates[{feature_index, field, value}], reason?)
```

- 只在用户**明确要求**并给出**具体目标值**时调用；问「该怎么改」不调用。
- 每次改写 `store.save_ir(stage="agent_edited")` 留版本快照 + `agent_part_edit` 审计。
- **值没变不算修改**：返回 `applied: false`，不留空版本。
- 被拒绝时返回 `{"error": …}` 而**不是抛异常** —— 工具报错应该变成模型看得懂的
  工具结果，让它把原因转述给用户，而不是中断整轮对话。

**文件系统只读这条约束没有放宽**：这个工具不碰文件系统，只按白名单改 IR。

### 18.4 审计要记「是谁让它改的」

Agent 跑在 worker 线程里，拿不到请求上下文，直接写就全记成 `system`。
`agent/send` 现在把用户名传进 `stream_sse(..., actor=...)`，worker 内部再
`_ACTOR.set()` 一次 —— **ContextVar 不会自动跨线程传播**，只在接口层设是没用的。

（`agent/send` 本来就要求 `WRITE_ROLES`，与 `workbench-chat` 一致，所以这不构成提权。）

### 18.5 界面刷新

改完要让右侧零件详情、3D 视图跟上，否则用户看到的还是旧值。

- `UI_ACTION_TOOLS["UpdatePartParameters"] = "refresh-ir"`。但这个事件是在工具
  **执行之前**发出的，当场刷新只会读到改写前的值 —— 所以前端先按 `tool_use_id`
  占位，等对应的 `tool_result` 回来解析出 `part_id` / `requires_regeneration`，
  **本轮结束后**再统一刷。
- 刷新本身复用 `app.js` 已有的 `refreshAfterChatEdit`（监听
  `cad-engine:workbench-chat-edit`）—— 它已经处理了重生几何、重拉 IR、刷新版本列表、
  重新选中零件。再写一份只会两边行为漂移。
- 只有 `applied === true` 才刷：工具被拒绝（零件不存在、字段不在白名单、值没变）时
  什么都没写。
- 工具卡副标题直接显示改了什么（`P-001 → 材料=SUS304，特征#1.thickness=0.8`），
  写操作不能只显示一个零件号。

### 18.6 测试

`tests/test_oc_agent.py` 新增 7 项：改写落盘且如实回报变更、不碰别的零件、

**把其余每个平台工具都跑一遍、断言 IR 原封不动**。
